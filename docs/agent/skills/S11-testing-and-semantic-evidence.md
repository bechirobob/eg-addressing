# S11 — Testing and Semantic Evidence

## Invoke when

Every task, especially before any PASS, verified, ready, or complete claim.

## Required inputs

- acceptance-criteria plan;
- implementation/model changes;
- independent expected sources;
- representative positive and negative cases;
- exact-head CI capabilities;
- applicable testing and release standard.

## Procedure

### 1. Create a claim-to-assertion matrix

| Claim | Observable assertion | Expected source | Test level | Negative case | Evidence artifact |
|---|---|---|---|---|---|

Every PR claim and AC status must appear.

### 2. Choose the correct test level

Use the lowest useful level plus enough integration evidence:

- static/type/schema checks;
- unit/domain rules;
- real PostgreSQL/PostGIS integration;
- API contract and authorization;
- component/workflow/browser;
- migration/restore;
- failure and recovery;
- security/abuse;
- accessibility/localization;
- performance/capacity.

Mocks cannot prove behavior dependent on real database constraints, PostGIS, object storage, identity, or container packaging.

### 3. Make expected truth independent

- reviewed registries and fixtures must be committed separately from observed generators;
- do not copy observed values into expected files during the same run;
- do not compare a generated file with a duplicate generated by the same function;
- manually review and sign off expected policy/mapping/transition sources.

### 4. Execute positive and negative behavior

A negative test must perform the forbidden action and assert:

- it fails;
- it fails for the expected reason;
- state remains unchanged or safely recoverable;
- audit/error behavior is correct.

A result string saying “rejected” is not a negative test.

### 5. Test semantics, not presence

For data/model work verify:

- exact values;
- types and nullability;
- relationships and target keys;
- controlled translations;
- classifications and authority;
- intervals and chains;
- public/protected projections;
- exception ownership;
- no-loss reconciliation.

For APIs verify method, path, operation, handler, roles, scopes, request/response/error fields, and classification.

### 6. Test generated artefacts

Generated artefacts require:

- deterministic regeneration;
- clean diff after regeneration;
- parser or real execution;
- source-to-generated parity;
- no self-modification;
- no hard-coded local paths;
- explicit statement of what the checker does and does not prove.

### 7. Bind evidence to exact head

After push, record:

- implementation SHA;
- workflow and run IDs;
- job IDs and conclusions;
- artefact IDs or report paths;
- changed-path proof;
- known skipped checks and reasons.

### 8. Report limitations

Every evidence report must distinguish:

- checks actually executed;
- checks inferred;
- checks not performed;
- institutional decisions still pending;
- scale or production assumptions not validated.

## Outputs

- claim-to-assertion matrix;
- positive/negative tests;
- exact-head reports;
- evidence limitation statement;
- criterion-specific evidence references.

## Stop or RFI conditions

Stop when:

- the expected result is generated by the observed logic;
- a negative behavior cannot be executed;
- a no-loss assertion is only prose or pseudo-SQL;
- green CI does not run the relevant test;
- a checker reports semantic PASS using counts/keywords only;
- production-scale claims lack representative data and targets;
- evidence requires unavailable authority or protected data.

## Evidence gate

Before claiming verified:

- all claim rows have named passing assertions;
- negative cases execute;
- expected sources are independent;
- exact-head CI ran the relevant jobs;
- evidence file is criterion-specific;
- limitations are explicit;
- no unchecked guarantee is summarized as PASS.

## Anti-patterns

- “24 checks, 0 errors” without naming the 24 assertions.
- Minimum row counts as proof of scenario correctness.
- Aggregate constraint counts as proof of required constraints.
- Keyword checks for route authorization or data classification.
- Checking target-field existence without transformation correctness.
- Marking skipped tests PASS because other CI jobs succeeded.
